# Netstack2 详细修复方案

> 状态: In Progress
> 审核基线: `2c35a09`
> 编写日期: 2026-08-12
> 目标: 将当前研究性 TCP 原型修复为可由 OpenPPP2 选择启用、可验证、可回退的多线程用户态 IPv4/IPv6 TCP/UDP 协议栈。

## 1. 结论与修复边界

当前仓库已经具备可复用的基础组件: buffer pool、Packet I/O 抽象、IPv4/IPv6 parser、分片重组、被动 TCP 握手、接收/发送缓冲、重传、AIMD/BBRv1/KCC-hybrid 原型、FQ-CoDel 原型、Linux TUN/TAP 和测试框架。

当前实现还不能替换 OpenPPP2 的 lwIP，主要阻断项如下:

| ID | 阻断项 | 当前后果 | 修复优先级 |
|---|---|---|---|
| R-01 | TCP Session 方向和回调接线错误 | 真实 TCP 代理不能双向传输 | P0 |
| R-02 | Dispatcher 未进入生产 RX 路径 | flow 不能稳定归属 shard，多队列配置可能越界或无人消费 | P0 |
| R-03 | Runtime 不等待异步 TX completion | Stop 后可能发生 pool UAF | P0 |
| R-04 | 公共配置没有接入 TCP 引擎 | MSS/RTO/窗口和 KCC/BBR 选择在生产中无效 | P0 |
| R-05 | UDP 只有 parser | 没有 UDP flow、转发、回包、超时和 UCP | P1 |
| R-06 | FQ-CoDel 是分配型简化实现 | 公平性存在 bug，不能满足 AQM/性能要求 | P1 |
| R-07 | KCC 定义与上游语义不一致 | 当前实现不是 UCP KCC2.0，生产默认仍为 AIMD | P1 |
| R-08 | OpenPPP2 只有 stub/fake smoke test | 没有真实 lwIP 替换路径 | P1 |
| R-09 | 只有 Linux TUN/TAP 后端 | DPDK/AF_XDP/Onload 和移动端/Windows 不可用 | P2 |
| R-10 | 没有真实 benchmark/interop/soak | 不能宣称性能、稳定性或可发布 | P0-P2 全程 |

修复期间必须遵守以下边界:

1. 在 R-01、R-02、R-03 完成前，不继续堆叠 DPDK、AF_XDP 或平台适配代码。
2. 在真实 OpenPPP2 构建和双向流量测试完成前，不得把 P4 标记为 Completed。
3. UDP parser 接线不等于 UDP 协议栈完成；只有双向 datagram、超时、错误处理和真实 adapter 通过后才能完成 P3U。
4. 内部存在某个 controller 类不等于运行时支持该算法；必须可配置、可观测并经过真实网络门禁。
5. stub、mock、NullPacketIo 和内存仿真只能证明接口或局部逻辑，不能作为平台支持或性能结论。

## 2. 目标架构

### 2.1 收包和 flow 分片

目标数据路径:

```text
IPacketQueue RX
    -> bounded L3/L4 classifier
    -> canonical FlowKey / FragmentKey
    -> owner_shard = StableHash(key) % shard_count
    -> direct process, or source_shard -> owner_shard SPSC lane
    -> IPv4/IPv6 reassembly and validation
    -> TCP/UDP flow state
```

必须保持的不变量:

1. 每个 RX queue 只有一个轮询线程。
2. 一个 shard 可以拥有 0 到 N 个 RX queue，不能假设 queue index 等于 shard index。
3. 同一双向 flow 在整个生命周期内只由一个 protocol-owner shard 修改。
4. queue owner 和 protocol owner 可以不同；跨 shard 只能传递拥有所有权的 packet/message，不能传递可写 PCB 指针。
5. 所有跨线程队列都有 packet、byte 和 message 数量硬上限。
6. flow 归属不依赖报文偶然进入哪个 TUN/NIC queue。

当前 `InboxSpsc` 不能直接作为所有 source shard 到同一 target shard 的公共 inbox，因为这会形成多 producer。第一版采用每个 `(source_shard, target_shard)` 一条有界 SPSC lane，由 target shard 轮询自己的所有 inbound lanes。若 shard 数量导致 O(N^2) lane 内存不可接受，再通过基准数据决定是否改为有界 MPSC ring；不能在没有数据时直接引入复杂 lock-free MPSC。

### 2.2 发包和 queue 所有权

目标发包路径:

```text
TCP/UDP protocol owner
    -> serialized BufferLease + flow_hash + ECN metadata
    -> selected TX queue owner
    -> per-queue FQ-CoDel/ECN scheduler
    -> IPacketQueue::SendBatch
    -> synchronous release or asynchronous completion
```

规则如下:

1. TX queue 也只能由其 owner shard 调用。
2. protocol-owner shard 不拥有目标 TX queue 时，通过 per-source SPSC egress lane 转交 `TxEnvelope`。
3. FQ/AQM 位于通用 IP egress，而不是 TCP 私有路径，因此 TCP 和 UDP 使用同一队列管理和内存上限。
4. `TxEnvelope` 保留原始 `flow_hash`，partial send 重入队不得重新归为 hash 0。
5. TX completion 完成前，pool 和 packet arena 必须保持存活。

### 2.3 TCP 与远端 Session 的正确方向

`ITransportSession` 必须只表示 Netstack2 到真实远端的传输腿，方向固定为:

```text
TUN client -> TCP RX -> ITransportSession::TrySend -> OpenPPP2/remote
OpenPPP2/remote -> DataCallback -> shard message -> TCP send buffer -> TUN client
```

以下语义禁止再次混用:

1. `TrySend()` 只用于把 TUN client 的 TCP payload 发送到远端 Session。
2. `DataCallback` 只用于把远端数据送入 TCP send buffer。
3. `TcpSession::OnDataReceived()` 不能绕开 frozen Session 语义，不能通过 `dynamic_cast` 形成生产和测试两套方向。
4. client FIN 表示远端 Session 的 `ShutdownWrite()`；远端 EOF 表示向 client 发送 FIN。
5. remote reset/error 映射为 TCP RST；不能仅删除 PCB 而不通知 client。

### 2.4 UDP 与 UCP 的边界

标准 UDP flow 和 UCP 必须分成两个工作包:

1. UDP core 负责 IPv4/IPv6 datagram 解析、校验、flow association、双向发送、空闲超时、PMTU、ICMP 错误和资源上限。
2. UCP 是 UDP 之上的可靠/拥塞控制传输 adapter，不得用 UCP 代替标准 UDP flow。
3. UCP/KCC2.0 的源码来源、commit、许可证、线程模型和算法 golden vector 必须先通过 ADR 固定。
4. 如果上游要求的 KCC 只属于 UCP，不应把它伪装成 TCP 拥塞控制算法；TCP KCC 是否保留必须由 ADR 明确决定。

## 3. API 修正版决策

现有 `v0.2.0` API 在功能完成前过早冻结。以下问题无法只靠内部实现可靠修复:

1. `NetstackConfig` 没有公开拥塞控制、AQM、CPU affinity 和 shutdown timeout。
2. `DatagramOpenResult` 只有无类型 `void*`，无法表达 datagram 生命周期和背压。
3. `DataCallback` 是无返回值的 owning callback，无法在 shard inbox 满时可靠反馈背压。
4. `IPacketQueue` 没有停止 RX、等待 TX completion 和确认 lease 已归还的生命周期方法。
5. `SessionOpenResult` 返回裸指针，Session 所有权和 callback quiescence 不明确。

必须先新增 ADR，例如 `ADR-008: API correctness reset`，再开始修改 public headers。建议发布 `v0.3.0`，并执行以下策略:

1. 先盘点是否存在测试仓库之外的真实 `v0.2.0` consumer。
2. 若没有已发布 consumer，直接做一次 source-level breaking correction，不增加无实际用户的兼容层。
3. 若存在已发布 consumer，旧入口只保留一个版本的 deprecated wrapper，并提供迁移表；内部只维护一套实现。
4. 每个 public signature 变更必须更新 `compile_contract_test.cpp` 和 consumer 示例。
5. ADR 必须说明二进制兼容、源码兼容、所有权、线程、失败和 shutdown 语义。

建议的 API 变更如下。

### 3.1 拥塞控制和队列配置

在 public API 中增加稳定枚举和配置:

```cpp
enum class TcpCongestionAlgorithm {
    Aimd,
    BbrV1,
    Kcc,
    HybridBdpAimd,
};

enum class AqmAlgorithm {
    None,
    FqCodel,
};

struct NetstackConfig {
    TcpCongestionAlgorithm tcp_cc = TcpCongestionAlgorithm::Aimd;
    AqmAlgorithm aqm = AqmAlgorithm::FqCodel;
    std::uint32_t fq_quantum = 1514;
    std::uint32_t codel_target_ms = 5;
    std::uint32_t codel_interval_ms = 100;
    std::uint64_t shutdown_timeout_ms = 5000;
    std::vector<int> shard_cpu_affinity;
    // Existing fields remain and must be wired into runtime.
};
```

`Kcc` 只有在实际 KCC 规范和来源固定后才能公开。当前自研实现应先重命名为 `HybridBdpAimd`，避免错误宣称。修复期默认使用 AIMD 作为保守 fallback；OpenPPP2 生产 profile 必须显式选择已经通过验收的 KCC 或 BBRv1，不能依赖隐式默认值。

### 3.2 Session 数据背压

建议把远端接收 callback 改为显式所有权和背压协议:

```cpp
enum class ReceiveStatus {
    Accepted,
    WouldBlock,
    Closed,
};

using DataCallback = std::function<ReceiveStatus(BufferLease&)>;

class ITransportSession {
public:
    virtual SendResult TrySend(BufferView data) = 0;
    virtual void ResumeReceive() = 0;
    virtual void ShutdownWrite() = 0;
    virtual void Abort(SessionError error) = 0;
    virtual void SetDataCallback(DataCallback cb) = 0;
    // Writable and closed callbacks remain.
};
```

所有权规则:

1. callback 返回 `Accepted` 时必须已经把 lease 移入 shard message，传入引用应为空。
2. callback 返回 `WouldBlock` 时不得移动 lease，Session 保留它并暂停继续读取。
3. shard inbox 和 TCP send buffer 回落到 low watermark 后调用 `ResumeReceive()`。
4. callback post 失败不得静默丢包；必须返回 `WouldBlock` 或关闭 Session。

建议将 `SessionOpenResult::session` 改为 `std::shared_ptr<ITransportSession>`。该引用只按 flow 创建/销毁，不进入每包热路径，可以明确保证 callback、PCB 和 Session 的生命周期。

### 3.3 Packet queue 停机契约

为每个 queue 增加明确的 quiesce 契约，名字可由 ADR 最终确定:

```cpp
class IPacketQueue {
public:
    virtual void StopRx() noexcept = 0;
    virtual IoError DrainTx(std::uint64_t deadline_ms) noexcept = 0;
    virtual std::size_t OutstandingTx() const noexcept = 0;
};
```

`DrainTx()` 返回后必须满足以下条件:

1. 不再调用 recv handler。
2. 不再产生新的 RX lease。
3. 已接受的 TX lease 已全部 completion 或被安全取消并归还。
4. queue/backend 不再持有 pool 指针。

同时为 `Netstack2` 增加可报告结果的停机入口，例如 `StopResult Stop(const StopOptions&) noexcept`。超时返回后对象保持 `Stopping` 且资源继续存活，调用方可以继续 drain；析构函数必须执行不带超时的最终安全回收或调用 backend 的同步 cancel，任何路径都不能先释放 pool。

### 3.4 UDP Session 类型

删除 `DatagramOpenResult::void* handle`，增加有类型的 `IDatagramSession`。接口至少表达:

1. 保留 datagram 边界的 `TrySendDatagram()`。
2. 远端 datagram callback 和背压。
3. source/destination endpoint metadata。
4. close/error 回调。
5. PMTU/最大 datagram 大小。
6. 明确的 Session 所有权。

实现步骤:

1. 删除 `DrainSession()` 中基于 `dynamic_cast<TcpSession*>` 的方向分支。
2. TUN client payload 始终通过 `ITransportSession::TrySend()` 发送到远端。
3. `BindSessionCallbacks()` 注册 Data/Writable/Closed 三类 callback。
4. Data callback 使用 `FlowId + generation` 投递 `kSessionData`，不得直接修改 PCB。
5. `kSessionData` 把远端数据加入 `TcpSendBuffer`；若只接受部分数据，PCB 保存 owning remainder 和 offset，不能释放未接受尾部。
6. 为每 flow 设置 `remote_rx_pending_bytes` 硬上限，并设置 high/low watermark。

1. 删除普通裸指针 `CallbackGate::owner`。
2. callback 只持有 `weak_ptr<ShardMailbox>` 或等价共享 mailbox，不持有 engine 裸指针。
3. mailbox 提供 `active`、`in_flight_callbacks` 和 `TryPost()`。
4. shutdown 先 deactivate，再清空 Session callbacks，再等待 in-flight callback 归零。
5. late callback 只能得到 `Closed/WouldBlock`，不得访问已销毁 shard/engine。

5. client half-close、remote half-close、simultaneous close。
6. remote reset、timeout、open reject。
7. callback 与 Stop 并发 10,000 次，TSan 无 race/UAF。
8. IPv4 和 IPv6 各跑一次完整双向 lifecycle。

### 4.3 R2: 修复生产 Dispatcher 和多 queue/shard 模型

目标: 任意合法 queue/shard 映射都不会越界、饿死 queue 或让 flow 跨 shard 修改。

实施状态（2026-08-12）:

- [x] 空 `rx_queue_to_shard` 仅在 `rx_queue_count <= shard_count` 时表示 identity mapping；否则 `Validate()` 在 Start 前失败。
- [x] Runtime 按显式 `rx_queue_to_shard` 将全部 RX queue 分配给其 owner shard；一个 shard 可轮转轮询多个 queue，未拥有 queue 的 shard 不轮询。
- [x] 覆盖 `{2,3}` 和 `{0,0}` 映射的实际收包回归测试。
- [x] 生产 RX 通过 `ClassifyPacket()` 在 TCP/UDP PCB 修改前按 canonical `FlowKey` 选定 owner；非 owner RX 通过 source-to-target lane 转交。IPv4/IPv6 TCP/UDP 片段先按稳定 fragment key 重组，完成的 TCP/UDP segment 再按 flow owner 处理。
- [x] 每个 `(source_shard, target_shard)` 使用独立、有 packet/message 和 byte 硬上限的 SPSC lane；target shard round-robin 轮询全部 inbound lanes，避免把多 source producer 放入公共 `InboxSpsc`。
- [x] TCP egress uses its FQ flow tag to select a deterministic TX queue. A
  protocol owner only retains callable pointers for its own queues; packets
  selecting a foreign-owned queue cross a dedicated bounded egress lane.
- [x] The queue owner re-admits a handed-off packet using its original enqueue
  timestamp before its local FQ-CoDel instance calls `SendBatch()`. Lane delay
  therefore contributes to CoDel sojourn accounting and unsent packets remain
  bounded by the scheduler/lane limits.
- [-] 当前实现中 TX queue 选择和 egress lane 已存在，但 FQ-CoDel 仍只用于 TCP 私有路径，尚未提升为 TCP/UDP 通用 egress scheduler（见 R6）。

实现步骤:

1. `Validate()` 明确验证默认 identity mapping，空 mapping 时要求 `rx_queue_count <= shard_count`；多个 queue 归属同一 shard 时必须给出完整显式 mapping。
2. Runtime 根据 `rx_queue_to_shard` 构建 `std::vector<IPacketQueue*>` 给每个 shard，不再使用 `queues_[i] -> shard[i]`。
3. shard event loop 对所拥有 queue 做 round-robin bounded polling，避免一个繁忙 queue 饿死其他 queue。
4. 增加只读取必要 header 的 `ClassifyPacket()`，返回 protocol、flow/fragment key、owner shard 和错误。
5. unfragmented TCP/UDP 使用 canonical FlowKey 分片。
6. IPv4/IPv6 fragment 先按 `{family, src, dst, protocol, fragment_id}` 进入同一 reassembly shard；重组完成后如 flow owner 不同，再转交完整 transport segment。
7. Dispatcher 返回明确的 `DispatchDecision`，不再接收却忽略 `StackShard* shards[]`。
8. direct packet 本地处理；redirect packet 移入 source->target SPSC lane。
9. inbox 满时增加按原因分类的 drop counter，TCP 不得创建半个跨 shard flow。
10. egress packet 根据 FQ flow hash 选择 TX queue；foreign-owned queue 通过
    bounded protocol-owner -> queue-owner lane 转交，并由 owner shard 发送。
11. shard 没有 RX queue 时可以作为 protocol owner，但必须由消息、timer 或 TX completion 正确唤醒，禁止固定 1 ms busy wake。
12. 实现可选 CPU affinity；失败原因写入 capability/metrics，不得静默声称已绑定。

新增测试:

1. `shard_count=1, rx_queue_count=2, mapping={0,0}`，两个 queue 都能收发。
2. `shard_count=4, rx_queue_count=2, mapping={2,3}`，只有 shard 2/3 轮询 queue，flow owner仍按 hash确定。
3. 多个 queue 映射同一 shard，不丢失第二个及后续 queue。
4. 同一 flow 正反向报文从不同 RX queue 注入，始终只有一个 PCB。
5. 4 个 source shard 同时向一个 target shard redirect，TSan 无 race。
6. lane saturation、shutdown drain 和 buffer return queue 无泄漏。

8. [x] 热路径 heap allocation hook 完成（`hotpath_alloc_test.cpp`：全局计数 operator new/delete，仅在该测试 binary 生效）：`FqCoDelSteadyStateHotPathNoHeapAllocation` 验证稳态 enqueue/dequeue 0 次分配（配合 FlowQueue 容量保持重构），`FlowReactivationReusesCapacity` 验证 flow 排空→重激活复用容量 0 次分配。TSan 下跳过（TSan 自带 new/delete 替换会冲突）。

验收:

- TCP 和 UDP 都经过相同 egress scheduler。
- 过载 10 秒内存不超过 hard limit。
- benchmark 中无每包通用 heap allocation，copy 次数有明确记录。

### 4.8 R7: 实现完整 UDP flow 和 UCP adapter

目标: IPv4/IPv6 UDP 可以通过 OpenPPP2 双向转发，并在此基础上可选接入 UCP。

主要文件:

- `include/tcpip2/session_factory.h`
- 新增 `include/tcpip2/datagram_session.h`
- `src/udp/input.cpp`
- `src/udp/udp.cpp`
- 新增 `src/udp/output.cpp`
- 新增 `src/udp/flow_table.cpp`
- `src/core/shard.cpp`

标准 UDP 实现步骤:

1. 合法 UDP datagram 创建或命中 shard-local `UdpFlow`。
2. 首包调用 `ISessionFactory::OpenUdp()` 并绑定有类型 Session。
3. client datagram 保持边界发送到远端；不得拼接成 stream。
4. remote datagram callback 投递 owner shard，序列化 IPv4/IPv6 UDP packet 回 TUN。
5. IPv4 checksum 0 按 RFC 处理；IPv6 checksum 强制有效。
6. 支持 UDP fragment reassembly；不能把完成的 UDP fragment 强制当 TCP 解析。
7. 增加 idle timeout、LRU/capacity eviction、per-flow byte limit 和全局 limit。
8. 处理 PMTU、IPv4 DF、IPv6 Packet Too Big 和 oversize datagram。
9. 无 Session 或策略拒绝时，根据产品策略返回 ICMP unreachable 或静默 drop，并可配置/可观测。
10. DNS、QUIC、fake-IP、route mark 和 VPN protect metadata 由 OpenPPP2 adapter 保留。

UCP 工作步骤:

1. 建立独立可选 target/module，核心库不强制依赖 UCP。
2. pin 上游 commit 和许可证，保存 NOTICE/provenance。
3. 把 UCP executor/timer 接入 shard 或受控 external executor，禁止 per-flow thread。
4. 适配 `BufferLease` 和 datagram Session，明确 copy/ownership。
5. KCC2.0 通过参考 golden vector 和 UCP peer interop。
6. capability 中只有真实构建并通过 runtime probe 时才报告 UCP 可用。

新增测试:

1. IPv4/IPv6 UDP echo 双向。
2. 0-byte、最大合法 payload、bad length/checksum。
3. fragment、PMTU、ICMP error。
4. flow timeout、capacity eviction、callback late arrival。
5. DNS/QUIC 多 flow 和多 shard。
6. UCP loss/reorder/latency 矩阵和真实 peer interop。

验收:

- `OpenUdp()` 在真实生产路径被调用。
- UDP 不再以“计数后丢弃”作为成功。
- UCP 未构建时明确报告 unavailable，不影响标准 UDP。

### 4.9 R8: 真实 OpenPPP2 集成和 lwIP 回退

目标: OpenPPP2 可以在启动时选择 `lwip`、`netstack2` 或现有 native engine，并完成真实双向 TCP/UDP 流量。

Netstack2 仓库工作:

1. 提供只依赖 public headers 的 install/export target 和版本信息。
2. 提供 production adapter contract test，不再包含 `core/runtime.h` 或 `session/tcp_session.h` 私有头。
3. 提供可供 OpenPPP2 实现的 `IPacketIo`、TCP Session、UDP Session 示例，不使用 fake transport 作为验收。
4. 输出 capabilities、selected CC、queue/shard mapping、fallback reason 和 metrics。

OpenPPP2 仓库工作:

1. 在 `VEthernet::PacketInput` 增加启动期三分支: `lwip|netstack2|native`。
2. 实现 `OpenPppPacketIo`，输入真实 raw IP，输出到现有 `ITap::Output`。
3. 实现 `OpenPppSessionFactory`，保留 Direct/Proxy、route mark、fake-IP、DNS、QUIC 和 PMTU 策略。
4. 实现真实 TCP remote Session 和 UDP datagram Session。
5. Netstack2 模式旁路 lwIP pbuf 和 loopback accept 双重 TCP 终结腿。
6. 保留 lwIP 回退，单实例只启用一个 engine，不做运行期 hot-switch。
7. Android socket 必须继续调用 VpnService protect；iOS/Windows 保留平台 tunnel 生命周期。

真实集成测试:

1. Linux netns TUN 下 HTTP/HTTPS 双向大文件。
2. TCP client/server 双向 half-close、RST、idle timeout。
3. UDP DNS、QUIC-like datagram、fragment 和 PMTU。
4. fake-IP、Direct、Proxy、route mark、DNS policy 回归。
5. 同一测试集分别跑 lwIP 和 Netstack2，比较 wire behavior。
6. Netstack2 启动失败时按配置回退 lwIP，并输出机器可读原因；strict 模式下直接失败。

验收:

- OpenPPP2 真实构建链接 Netstack2 public target。
- integration test 不使用 NullPacketIo 作为最终验收后端。
- TCP/UDP 双向业务、策略和 shutdown 全部通过。
- lwIP fallback 保持可用。

### 4.10 R9: 高性能后端和跨平台铺开

目标: 在 core correctness 和 OpenPPP2 集成稳定后，按 capability 增加后端。

#### Linux TUN/TAP

1. 用 epoll/eventfd 或等价机制唤醒 shard，删除固定 1 ms 轮询等待。
2. 验证 IFF_MULTI_QUEUE 的真实 queue ownership 和 TX 行为。
3. 记录每包 syscall、copy、wake 和 context switch。
4. TC/eBPF hairpin 作为可选 datapath，通过 runtime probe 决定；不可用时回退 TUN。

#### AF_XDP

1. 先实现 copy mode，验证 rings、fill/completion 和 shutdown。
2. zero-copy 前先完成 external-buffer ownership ADR。
3. queue、CPU、NUMA、UMEM 和 NIC RSS 配置必须可观测。
4. hairpin 和路由/邻居边界必须在验收中说明，不能只证明 RX/TX ring 可读写。

#### DPDK

1. 独立 optional CMake target，不污染标准 core build。
2. 实现 EAL/port/queue、mbuf ownership、TX completion 和 checksum offload。
3. 明确 DPDK 是 Packet I/O backend 还是 remote Session backend；两者不能混称。
4. 实现 route/neighbor/L2 或明确只运行在已有 L3 tunnel adapter 后。

#### Onload

1. 实现 `OnloadSocketSession`，复用 TCP remote Session contract。
2. Onload 走 socket acceleration，通常不是 TUN Packet I/O backend。
3. 运行时探测库、NIC 和 stack mode，失败时回退 kernel socket。

#### Android/iOS/Windows

1. CMake 对 Linux headers 和 `tap_io.cpp` 加平台条件，首先做到三平台可编译。
2. Android 实现现有 TUN fd adapter，并保留 `VpnService.protect(fd)`。
3. iOS 实现 `NEPacketTunnelFlow` batch adapter，控制 copy 和 callback 生命周期。
4. Windows 实现 Wintun ring adapter，在 release receive packet 前复制/转移所有权。
5. 移动端增加 event mode、功耗、后台/前台切换和内存压力测试。

每个后端的完成定义:

- 构建通过。
- 双向 interop 通过。
- shutdown/completion 通过。
- 1 小时 stress 和 24 小时 soak 通过。
- capability 与实际 probe 一致。
- 有独立性能记录，不使用其他后端的数据代替。

### 4.11 R10: 验证、性能和发布门禁

目标: 用可复现证据回答“是否比 lwIP 快、是否多核扩展、是否可发布”。

#### 功能测试

1. 单元测试覆盖 parser、state machine、queue ownership 和算法状态。
2. stateful fuzz 覆盖 TCP flags/sequence/options、UDP、IPv4/IPv6 fragment 和 extension headers。
3. differential test 与 Linux TCP/lwIP 比较 checksum、ACK、retransmit、close 和 PMTU。
4. packet capture 保存失败输入，回归测试固定为仓库资产。

#### 真实网络测试

使用 Linux network namespace、veth、TUN、`tc netem` 和真实 socket/session，至少覆盖:

| 维度 | 矩阵 |
|---|---|
| RTT | 1/20/100/300 ms |
| Loss | 0/0.1/1/5/10% |
| Reorder | 0/1/5% |
| MTU | 1280/1400/1500 |
| Flow 数 | 1/100/1,000/10,000 |
| Shard 数 | 1/2/4/8/16 |
| IP | IPv4/IPv6 |
| Transport | TCP/UDP/UCP optional |

#### 性能指标

benchmark 必须同时运行 lwIP 和 Netstack2 的同场景 harness，记录原始 JSON:

1. 单流和多流 throughput。
2. packet/s 和 byte/s。
3. P50/P95/P99 latency。
4. CPU/byte、每 shard CPU、context switch 和 wakeup。
5. 每包 heap allocation、copy 次数和 copy bytes。
6. pool miss、inbox drop、AQM mark/drop 和 retransmit。
7. 1/2/4/8/16 core scaling efficiency。
8. elephant+mice latency 和 Jain fairness。
9. 功耗和温度，移动平台单独记录。

初始性能门禁沿用现有 implementation guide，并在 P0 实测后冻结:

1. steady-state packet hot path 每包 0 次通用 heap allocation。
2. 单 shard throughput 不低于同场景 lwIP，且 CPU/byte 不更差。
3. 4 shard aggregate throughput 至少达到 1 shard 的 3 倍。
4. 8 shard aggregate throughput 至少达到 1 shard 的 5 倍。
5. elephant+mice 场景 mice P99 不高于 FIFO 的 50%。
6. 过载 10 秒后所有 queue memory 保持在 hard limit 内。
7. Stop 到所有线程/completion quiesced 的 P99 小于 2 秒。
8. 24 小时 soak 后 buffer、flow、timer、fd 和线程净增量为 0。

达不到门禁时保留原始数据并标记 blocker，禁止删除样本或改统计口径后宣称成功。

## 7. 可观测性要求

没有可观测性就不能定位性能或正确性问题。每个 shard/queue 至少输出:

1. RX/TX packet 和 byte。
2. classifier/parser/checksum/fragment/inbox/AQM/backend drop reason。
3. flow count、half-open、TIME-WAIT、UDP association 和 eviction。
4. cross-shard redirect packet/byte 和 lane high watermark。
5. pool free/outstanding/return queue/miss。
6. FQ active flow、queue bytes、CoDel drop、ECN mark。
7. selected CC、cwnd、pacing、RTT、delivery rate、loss/retransmit。
8. async TX outstanding/completion latency。
9. callback queue depth、WouldBlock、late callback 和 shutdown duration。
10. backend capability 和 fallback reason。

高频 metric 在 shard 内累积，周期性发布；不得在每包路径格式化日志或争用全局 mutex。

## 8. 文档状态规则

里程碑只能使用以下状态:

| 状态 | 含义 |
|---|---|
| Planned | 只有方案，没有生产代码 |
| Prototype | 有局部实现或 fake/mock 测试，未进入真实数据路径 |
| In progress | 已进入生产路径，但验收门禁未全部通过 |
| Completed | 所有功能、并发、interop、shutdown 和要求的性能门禁都有证据 |

状态更新必须同时修改 README、roadmap 和对应 plan，并附:

1. commit。
2. 测试名称和结果。
3. 真实后端/平台。
4. 性能 record 路径。
5. 已知限制。

禁止用“代码文件存在”“单元测试通过”或“接口可编译”单独作为 Completed 依据。

## 9. 最终完成定义

只有以下项目全部通过，Netstack2 才可以作为 OpenPPP2 的可发布 TCP/IP engine:

- [ ] IPv4/IPv6 TCP 双向数据、重传、窗口、SACK、close、RST 和 PMTU 通过真实 interop。
- [ ] IPv4/IPv6 UDP 双向 datagram、fragment、timeout、ICMP 和 PMTU 通过真实 interop。
- [ ] UCP 按 capability 可选，来源、许可证、KCC 和 peer interop 有证据。
- [ ] 同一 flow 在多 queue 输入下始终由唯一 shard 修改。
- [ ] 所有合法 queue/shard mapping 通过；非法配置在 Start 前失败。
- [ ] KCC/BBRv1 可在新 flow 创建时选择并报告实际算法。
- [ ] FQ-CoDel/ECN 覆盖 TCP/UDP、内存有界且热路径无每包通用 heap allocation。
- [ ] Stop 等待 Session callback 和异步 TX completion，所有 pool outstanding 为 0。
- [ ] OpenPPP2 route/DNS/fake-IP/PMTU/VPN protect 行为无回归。
- [ ] lwIP fallback 可用，Netstack2 失败原因可观测。
- [ ] Linux TUN multiqueue 达到性能门禁。
- [ ] AF_XDP/DPDK/Onload 只在真实实现和 runtime probe 成功时报告可用。
- [ ] Android、iOS、Windows 分别通过 build、interop、shutdown、stress 和 soak。
- [ ] 普通、ASan/UBSan、TSan、fuzz、netem、differential 和 24 小时 soak 全部通过。
- [ ] 同机同场景性能报告证明达到已冻结门禁。

默认切换顺序:

```text
开发环境 opt-in
    -> Linux canary, lwIP fallback enabled
    -> 小比例用户启用并观察错误/性能
    -> Android/iOS/Windows 分平台 canary
    -> 满足全部门禁后才考虑默认 netstack2
```

在完成清单全部关闭前，OpenPPP2 默认 engine 不得切换为 Netstack2。
